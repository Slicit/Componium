# feat-timeline-v2 — a timeline a video editor would accept

Status: **proposed, not started.** Written 2026-08-29 after the first editable
timeline landed and was judged "kinda ok, but not what I expected" by someone
who edits video for a living. That is the right verdict and this file is the
response.

## The diagnosis

The current timeline is a *viewer with dragging bolted on*. That is a
different thing from an editor, and the gap is not a list of missing buttons,
it is four missing foundations:

- **No selection model.** One cue can be "selected" for the inspector. There
  is no multi-select, no box select, no notion of a selected time range, and
  therefore nothing for any bulk operation to operate on.
- **No undo.** Every edit is immediate and permanent until you decline to
  save. This alone disqualifies it as an editing tool: an editor tries things.
- **No clipboard, no zoom, no timecode.** A feature film is drawn squashed
  into 1000 arbitrary units, addressed in `MM:SS.mmm` rather than
  `HH:MM:SS:FF`, and cannot be examined closer than the whole film at once.
- **It does not scale.** See below; this is measured, not feared.

There is also a plain defect against goal #1. A cue is drawn as a uniform gold
block **whose appearance does not encode its amplitude at all**: a 0.2 gust and
a 1.0 gust are the same rectangle. The one thing the timeline exists to show —
timing *and* amplitude — is currently half absent.

## The measurement that decides the architecture

Real scores, generated by our own composer:

| score | duration | curve points | cues | points/second |
|---|---|---|---|---|
| `sintel` | 14m48s | 5,511 | 12 | 6.2 |
| `big-buck-bunny` | 9m56s | 3,196 | 25 | 5.4 |
| `crab-dance` | 0m36s | 141 | 0 | 3.9 |

At roughly six points per second, **a two hour feature is about 45,000 curve
points**. The timeline draws one SVG circle per point *per channel*, so an RGB
light track alone is about 135,000 DOM nodes, plus polylines, rebuilt on every
render. Sintel already costs ~16,500 circles today.

That settles one question permanently: **the event surface cannot be DOM.** No
amount of React makes 135,000 nodes scroll at 60fps. Professional editors draw
their timelines to a canvas, and so must this one.

It also settles a second: virtualisation is not optional. Only the visible time
window may be drawn, whatever the zoom.

## The decision

**Yes to React and TypeScript, with a Vite build — but the timeline surface is
canvas, and the editing logic belongs to neither.**

Three layers, and the middle one is the point:

```
  app shell        React + TypeScript
                   panels, menus, dialogs, inspector, library, transport
                   ── knows about the DOM, knows nothing about editing rules

  timeline surface canvas 2D, one component, imperative
                   draws a time window; hit-tests; emits intents
                   ── knows about pixels, knows nothing about React

  editing core     plain TypeScript, zero dependencies, zero DOM
                   document model, commands, undo, selection, snapping,
                   time/frame arithmetic, validation
                   ── knows the rules, and can be tested in Node
```

The editing core is the part that matters and the part to build first. It is
also the answer to this project's chronic verification problem: the sandboxed
browser here blocks subresources on LAN origins and never delivers animation
frames, so *nothing about a running page can be trusted here*. A core with no
DOM is testable with `node`, exhaustively, offline. Everything this session got
wrong — the pointer-capture bug, the squashed hit targets, the `Number(null)`
default — was invisible to the tests precisely because it lived in the layer
that only a real browser exercises. Shrinking that layer is a correctness
strategy, not just a tidiness one.

### What this reverses, and why that is honest

`internal/studio/studio.go` opens by saying the studio has no build step and no
`node_modules`, because "the cost of a JavaScript toolchain falls on every
contributor rather than on the one person who wanted it". That was right when
the studio was a list of cues.

It is no longer right, because the alternative has changed. The choice is not
"toolchain vs no toolchain" any more; it is "a Vite config vs a hand-rolled
non-linear editor in vanilla JavaScript". The second is far more hostile to a
contributor than the first. A `npm ci && npm run build` is a thing every web
developer already knows; a bespoke 6,000-line canvas editor with its own
undo stack and event model is a thing only its author knows.

**Cost to pay explicitly:** `go build ./...` alone stops producing a working
studio, because `go:embed` needs `dist/` to exist. The options are (a) commit
`dist/`, as we already commit three.js, (b) build it in CI and in the
Dockerfile only, or (c) both, with CI verifying the committed `dist/` is
current. **Recommendation: (c).** It keeps `go build` working for anyone who
just wants the binary, keeps the toolchain optional for Go contributors, and
the CI check stops the committed bundle going stale — which is the only real
failure mode of committing build output.

### What does *not* change

- The Go server, the score format, the parser, the conductor: untouched.
- `room3d.js` already exposes a class with a four-call interface and no
  framework assumptions. It becomes a React component wrapping the existing
  class behind a `ref`. Low risk, no rewrite.
- The score stays the canonical, hand-editable artefact. No UI state goes in
  it (see track order, below).

## Part 1 — Showing the score truthfully

The first goal, and the one the current version half fails.

- **Amplitude is encoded, always.** A cue block's fill is a ramp on its
  intensity, and its height is proportional too — so a row of gusts reads as a
  bar chart of strength at a glance, which is exactly how a mix is read.
- **Spans look like spans.** Start and end caps, a body, and a distinct
  hatched tail for the latency lead-in (below). A momentary cue is a marker
  shape, not a thin rectangle, so the two are never confused at any zoom.
- **Curves get a real value axis** with gridlines at 0, 0.5, 1, a filled area
  under the line (area reads amplitude far faster than a bare stroke), and the
  value under the playhead printed numerically in the track header.
- **Nominated vs confirmed.** The composer *nominates* water and plunges
  rather than detecting them. Nominated events are drawn outlined rather than
  filled, and there is a filter for "unconfirmed only". This concept already
  exists in the analysis and is currently invisible in the editor.
- **Density-aware drawing.** Zoomed out, 45,000 points must not be 45,000
  strokes: the renderer draws a min/max envelope per pixel column, the way an
  audio editor draws a waveform. Zoomed in past ~1 point per 8px, it switches
  to discrete points with handles. Same data, two honest representations.

## Part 2 — Track groups, sub-lanes, expand/collapse

- A **track group** is one instrument. Its channels are sub-lanes.
- **Collapsed** is not "hidden": an RGB group collapses to a single
  **colour ribbon** — a horizontal gradient of the actual colour the light is
  driving over time. For a colour curve this is *more* informative than three
  value lines, and it is what an editor expects from a collapsed layer.
  Non-colour groups collapse to a filled amplitude envelope.
- **Expanded** shows one lane per channel, as now but properly.
- Group header carries: name, kind glyph, mute, solo, lock, collapse chevron,
  colour swatch, and the live value at the playhead.
- Heights are draggable per group and remembered.

## Part 3 — Interaction

### Keyboard

A seasoned editor's hands go to **J K L** before anything else, so that ships
in the first interactive phase, not the last.

| key | action |
|---|---|
| `J` / `K` / `L` | shuttle back / stop / forward; repeated presses multiply speed |
| `space` | play–pause |
| `←` `→` | one frame |
| `shift`+`←` `→` | one second |
| `,` `.` | nudge selection one frame |
| `home` `end` | start / end |
| `I` `O` | set in / out point of the work range |
| `S` | split the event at the playhead |
| `X` | ripple delete the work range |
| `M` | drop a marker |
| `+` `-` | zoom at playhead; `F` fit; `shift`+`Z` zoom to selection |
| `⌘/ctrl`+`Z` / `⇧⌘Z` | undo / redo |
| `⌘/ctrl`+`C` `X` `V` | clipboard, across tracks and across films |
| `alt`+drag | duplicate |
| `⌥`/`shift` while dragging | disable snapping / constrain axis |

### Frame accuracy is a real problem and needs saying

The score already carries `fps` (`score.Meta.Media.FPS`, `24.0` in our
generated scores), so the arithmetic is available. The difficulty is the
browser: `HTMLVideoElement.currentTime` is not frame-exact, and seeking gives
you the nearest decodable frame, not the one you asked for.

The workable approach is `requestVideoFrameCallback`, which reports
`mediaTime` and `presentedFrames` for the frame actually on screen, so stepping
becomes "seek to `(n + 0.5)/fps` and confirm which frame arrived" rather than
"assume". It is supported in Chrome and Safari and **not in Firefox**, which
needs a documented degraded path: seconds-accurate stepping and a visible note,
rather than silently lying about frame numbers.

Timecode display becomes `HH:MM:SS:FF` throughout, with `MM:SS.mmm` available
as an option. Editors think in frames.

### Right-click menus

Context-sensitive, because a menu that shows every action everywhere is a list,
not a menu:

- **on a cue** — cut/copy/duplicate, delete, split at playhead, set duration…,
  set intensity…, convert to span / to momentary, ease in/out, snap to
  playhead, reveal in inspector
- **on a curve point** — delete, set value…, set time…, smooth neighbours,
  make linear/step/ease, add point before/after
- **on a selection** — scale amplitude…, time-stretch…, quantise, reverse,
  thin points…, delete
- **on a track header** — rename, colour, mute/solo/lock, expand/collapse,
  move up/down, clear track, rebuild this track from analysis
- **on empty space** — paste, add cue here, add point here, add marker, zoom
  to fit, select all in this track

### Track reordering, and where the order lives

Reorder by dragging the group header, with a drop indicator.

The order must **not** go in the score. The score is the artefact the player
consumes and a human hand-edits; putting view state in it means every cosmetic
drag dirties a file that the conductor reads. Instead a sidecar
`<film>.layout.json` beside the score holds order, heights, collapse state,
colours and markers. Missing sidecar means sensible defaults; deleting it loses
nothing but arrangement. (The alternative — a `[ui]` table in the score —
survives copying the score around, but pollutes it. Sidecar is the
recommendation.)

## Part 4 — Zoom, pan, and range

- Time window `[t0, t1]` is the single source of truth for the view.
- Wheel zooms about the cursor; `shift`+wheel pans; drag on the ruler scrubs;
  middle-drag pans; pinch on trackpads.
- **Overview strip** under the main surface showing the whole film with the
  current window as a draggable box — the fastest way to move around a
  two hour timeline.
- **Work range** (in/out) shaded, with operations that respect it.
- **Filters**: by instrument kind, by "has events in view", by unconfirmed
  nominations, and a text filter on instrument id.
- **Snapping** to playhead, markers, work range, other events, and whole
  seconds/frames — with a toggle and a modifier to suspend it.

## Part 5 — What makes it *Componium's* timeline

A generic NLE timeline would leave the most valuable information invisible.
These are the features no library gives us and the reason to build rather than
adopt:

- **Latency ghost.** Every instrument declares dead time; the conductor
  dispatches that much early. The timeline should draw both: the authored time
  as the solid event, and the actual dispatch moment as a ghost ahead of it,
  joined by a thin lead-in. A 1.2s fan lead is the single most surprising thing
  about authoring for this system and it is currently invisible.
- **Calm regions.** The dynamics pass computes rest; those regions become a
  shaded band across the whole timeline, so "why did nothing fire here" has a
  visible answer, and so an operator can see when they are about to author into
  someone's rest.
- **Safety overlays.** Duty-cycle windows and `MaxContinuous` are properties of
  the rig; a span that violates them gets red hatching *while you drag it*,
  not on save. The editor should make an unsafe score hard to draw.
- **Precision gating.** Cues carry `RequiredPrecision`; when the current clock
  cannot meet it, those cues are drawn as at-risk. This is already modelled and
  never shown.
- **A composite "felt" lane** at the top: everything the audience experiences,
  summed, so the shape of the whole show is visible in one strip.

## Part 6 — Testing, given where this is developed

Hard-won this session and non-negotiable:

- **Core** — plain Node tests. Commands, undo, snapping, time arithmetic,
  validation. Fast, exhaustive, no browser.
- **Renderer** — the canvas renderer emits a **draw list** (an array of typed
  primitives) which is then executed against a real context. Tests assert on
  the draw list: "at this zoom, this cue is drawn at x=… with this fill". No
  GPU, no frames, and it catches exactly the class of bug that a screenshot
  would show and a unit test currently cannot.
- **Interaction** — the headless-Chrome CDP harness already built
  (`hack/shoot-studio.sh` and the `/tmp/cdp` driver) drives real pointer and
  keyboard input against the real page. This is what caught the pointer
  capture bug; it becomes a committed part of the suite rather than a scratch
  script.
- **Performance budget as a test.** A generated 2-hour score, 45,000 points:
  render a frame under 8ms, and fail CI if not.

## Phases

Each phase ends with something usable. No phase is a big-bang rewrite.

**Phase 0 — the core, headless.** Document model, command/undo stack,
selection, time & frame arithmetic, snapping, validation against rig
constraints. No UI change at all; the existing timeline keeps working. Ends
with a large Node test suite. *This de-risks everything after it.*

**Phase 1 — the shell and the surface, read-only.** Vite + React + TS, the
canvas timeline replacing the SVG one: ruler, timecode, zoom, pan, overview,
groups with collapse, amplitude encodings, min/max envelope drawing. Editing is
still the old inspector. Ends with the performance test passing on a 2-hour
score.

**Phase 2 — editing on the new surface.** Drag, trim, add, remove, multi-select,
box select, clipboard, undo — all through the Phase 0 commands.

**Phase 3 — the editor's hands.** Full keyboard map, J/K/L, frame stepping with
`requestVideoFrameCallback`, context menus everywhere, markers, work range.

**Phase 4 — arrangement.** Track reorder, heights, colours, layout sidecar,
filters, saved views.

**Phase 5 — the Componium overlays.** Latency ghosts, calm bands, safety
hatching, precision warnings, composite felt lane.

Phases 0–2 are the ones that change the verdict. 3–5 are what make it good.

## Risks and what I would cut first

- **Scope.** This is weeks, not days. The mitigation is the phase boundaries:
  after Phase 2 it is already a better tool than today, and stopping there is a
  legitimate outcome.
- **The build step is a real cost** and the CI freshness check is the thing
  that stops it becoming a footgun. Do not skip it.
- **Firefox has no `requestVideoFrameCallback`.** Frame-exact stepping degrades
  there; say so in the UI rather than lying.
- **First to cut if time is short:** the composite felt lane, time-stretch,
  saved views, and ripple/roll edits. **Never cut:** undo, and the performance
  budget test.
